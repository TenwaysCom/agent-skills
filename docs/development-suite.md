# 用开发套件交付需求

在一个可独立发布和回退的需求上使用本指南。先按[安装指南](install.md)安装所需 skills，再在目标项目中调用它们。

项目需要 UAT 晋级、两阶段 PR 或协调发布批次时，保留需求和已有证据，转交项目专用流程。

## 建立需求记录

调用 `dev-requirements`，提供用户问题和已有 Issue。同一需求继续使用原 Issue。

```text
用 $dev-requirements 整理这个需求，复用已有 Issue，写出范围、验收条件和研发任务。
```

将当前目标、范围、需求版本、AC 和需求变更表集中放在 Issue 正文的“需求”章节。每个 AC 包含前置条件、操作和可观察结果，并使用稳定编号，例如 `AC1`。

首次建单时同步需求基线。缺少远端访问能力时，先保存本地草稿并标记未同步，不将草稿记为已更新到 GitHub。

在相关 commit 和 PR 中使用 `Refs #编号`。仍有发布或验收条件未完成时，避免使用 `Closes #编号` 等自动关闭关键词。

## 累计记录并按检查点同步

沿用项目约定的本地记录位置。没有约定时，可使用 `.local/dev-records/issue-123.md`。记录每次实质需求变化、受影响 AC、候选版本、测试及 review 结论、证据位置和剩余事项。恢复工作时，同时读取最新 Issue 和本地待同步记录，核对他人更新及未同步内容。

按以下节点更新 Issue。

| 节点 | 操作 |
| --- | --- |
| 首次建立需求 | 写入目标、范围、AC 和初始需求版本 |
| 日常调整、自测、局部修复和复查 | 累计本地记录，暂不发布 Issue 进度评论 |
| 正式交付候选供 review 或验收 | commit、push 并读回 SHA 后，统一同步需求变化、改动、检查结论、剩余事项和 PR |
| 需他人决策或影响协作的变化、阻塞 | 及时同步问题、影响、现状和解除条件，可在 push 前进行 |
| 必须交接未提交或未推送的工作 | 明确实际代码状态，提供记录与证据位置 |
| 一轮正式验收形成结论 | 同步实际版本、环境、执行者、AC 结果和下一步 |
| 合并、部署、回退结束或中止 | 同步最终提交、实际运行版本、冒烟及恢复结果，说明剩余验收 |

普通 push 不单独触发同步。正式候选交付前，核对证据是否覆盖最终提交。推送失败时保留未同步状态，不回填无法读回的提交链接。同一 SHA 出现新的验收或部署结果时，更新相应结论，无需新增提交。

交接时可调用 `dev-requirements` 汇总本轮已有记录。

```text
用 $dev-requirements 同步 Issue #123 的本轮交付记录。核对已推送候选的远端 SHA，集中更新需求、变更、测试、review 和剩余事项。
```

将 `#123` 替换为实际 Issue 编号。同步记录本身不授权 commit、push、合并或部署。只要求起草时保留本地文本。

每个同步节点都合入已确认的待同步需求及变更，保持正文需求版本与各阶段结论一致。更新前重读远端，保留他人内容、需求历史和旧候选证据索引。正文注明最近同步节点、时间和候选版本。每个正式交接至多一条摘要评论，重复同步同一节点且内容无实质变化时跳过写入。写入后读回，再将对应本地内容标为已同步；响应不明时先查询，避免重复评论。

完整日志和截图保留在证据位置，正文写结论及索引。向协作者提供可访问的证据；只有本地文件时说明限制。连续完成的合并、部署及验收可在同一次交接汇总，需介入的失败及时同步。详细操作见 [Issue 同步规则](../skills/dev-requirements/references/issue-sync.md)。

## 实现并测试改动

使用项目已有的开发工具实现需求。完成候选改动后，调用 `dev-test`。

```text
用 $dev-test 对 Issue #123 的当前改动做自测，记录实际结果、证据和未覆盖场景。
```

核对本地测试记录中的需求版本、代码版本、环境、操作和实际结果。未提交改动使用 diff 或产物指纹，不能把结果记到干净 HEAD 上。将结果纳入本轮记录，到交付检查点集中同步。

保留失败和未执行的检查。配置检查、mock 测试和本地测试分别说明覆盖范围，不替代真实集成结果。

## 审查候选版本

调用 `dev-review`，提供当前 PR 或 diff。

```text
用 $dev-review 审查这个 PR，只报告问题和可合并结论，先不要修改代码。
```

只要求 review 时，接收问题清单和证据。需要修复时，在请求中明确修复范围。修复后重新测试并复查受影响部分。

检查结论是否覆盖当前目标分支 base、PR head 和需求版本。只完成作者自查时，保留作者自查标记。具体 review 讨论保留在 PR，本轮结论累计到待同步记录，局部修复不逐条播报到 Issue。

## 验收候选环境

有预览环境时，调用 `dev-acceptance` 验证业务行为。

```text
用 $dev-acceptance 在预览环境验收 Issue #123，保留需要部署后验证的条件。
```

按 AC 逐项执行操作，记录环境、版本、执行者、实际结果和证据。项目要求人工业务确认时，取得该人的实际结论。一轮验收形成通过、失败或阻塞结论后集中同步，不逐项发布进度。

预览通过后进入待发布。依赖实际交付环境的条件保持未完成。没有预览环境时，将对应检查安排到部署后。

## 准备并执行发布

先调用 `dev-release` 准备可审阅的发布方案。

```text
用 $dev-release 准备这个 PR 的 prod 发布方案，列出版本、验证、风险和回退方式。
```

检查候选证据、目标环境、发布入口和回退方式。仅要求准备方案时，到方案交付为止。

需要实际操作时，明确操作和目标环境。已有明确授权继续有效，无需再次取得。

```text
用 $dev-release 合并这个 PR 并发布到 prod，沿用项目已有发布方式，完成运行版本读回和关键业务冒烟。
```

如果合并会自动部署，在合并前确认以下任一约束有效。

- 分支保护或合并队列要求当前 base 与 head 的组合通过检查，版本变化后使旧结果失效。
- 部署前检查要求最终合并产物通过验证后才能部署。

无法确认这些约束时，保持待处理，不触发会自动部署的合并。单次本地预合并通过不能代替持续有效的发布约束。

## 完成实际环境验收

部署后再次调用 `dev-acceptance`。

```text
用 $dev-acceptance 验收 Issue #123 在实际交付环境中的运行版本，给出逐项结果和是否可关闭的结论。
```

核对实际运行版本，验证入口和全部适用 AC。补齐使用方法、最终提交和证据。部署成功但验收尚未完成时，保持 Issue 打开，标记已发布待验收。

全部交付条件满足后，按已有关闭授权更新并关闭 Issue，再读回最终状态。没有关闭授权时，交付可关闭结论和更新草稿。

## 处理变更和失败

需求变化时，先更新本地记录中的需求版本，保留各次变更决定，重开受影响 AC。在下个检查点合入 Issue 正文。需他人决策或影响协作的变化及时同步。代码、依赖、配置或环境变化时，重新判断已有证据的适用范围，补跑受影响检查。

验收失败时，记录复现步骤、实际结果和预期差异。同一需求的修复继续使用原 Issue。

同一轮使用尚未合并的 PR。原 PR 已合并后，修复使用新的补丁 PR，并关联原 Issue。记录补丁候选和最终发布版本，不用旧 PR 的 SHA 代表修复。

发布关键检查失败时，保存证据并停止继续发布。按已授权且适用的项目方式回退，再核验实际恢复结果。

## 将同步节点写入项目规则

用户要求初始化或更新项目流程时，在现有 tracker 或贡献指南中加入以下约定，并从 AGENTS.md 链接该文档。将原有逐轮完成播报要求统一为检查点同步，保留其他项目规则。

```text
同一需求复用原 Issue。正文集中保存需求和需求变更表，开发中的调整及检查结果先累计到本地待同步记录。
首次建单、候选交付、正式验收、发布结果和必要的中途交接是同步节点。需他人决策或影响协作的变化及时同步。
正式候选交付在 commit、push 并读回远端 SHA 后集中更新。普通 push、单条测试或局部修复不单独触发更新。
每次同步合入已确认的待同步需求及变更，保持正文需求版本与结论一致。写入前重读远端，保留他人内容、需求历史和旧候选证据。每个正式交接至多一条摘要，无实质变化时跳过写入，写入后读回。
合并、部署、验收分别记录实际结果。全部交付条件满足后，按已有授权关闭 Issue。
```
