# 管理简单项目需求

以同一个 Issue 管理一个可独立交付的需求。需求持续记录，远端按交付检查点集中同步。先写清用户问题和可观察结果，再组织开发任务。

## 识别项目与需求

1. 读取仓库的 AGENTS.md、贡献指南、现有 Issue 模板和交付约定。确认实际仓库、默认分支及当前工作区，保留无关改动。
2. 按实际交付方式分类。一个 PR 合入默认分支、可以独立发布和回退时，采用简单流程。需要 UAT PR 再到 main PR、发布批次或跨系统协调晋级时，记录原因并移交项目专用 skills。不要自动生成两阶段流程。
3. 搜索已有 Issue。同一需求继续维护原 Issue，独立需求另建并关联。缺少访问能力时先写本地 Markdown 草稿，标记未同步，不阻塞无依赖的本地工作。
4. 写明谁在什么场景遇到什么问题、当前行为、预期行为和范围。缺陷补充复现步骤。影响正确性、数据或验收标准的未知项列为待澄清，其余使用可撤销的合理假设并说明。

需要了解这组 skills 的分工及设计理由时，读取 [设计说明](references/design.md)。日常建单不必加载它。

## 建立与维护记录

没有合适的现有结构时，使用 [Issue 模板](assets/change-request.md) 的章节。用模板创建 Issue 正文时去掉 YAML frontmatter 和填写提示。首次需求记为 r1，后续实质变更递增需求版本。

- 用稳定的 `AC1`、`AC2` 编号填写验收条件。每项写明前置条件、操作和可观察结果，不写“功能正常”。
- 将研发任务写成可独立验证的交付结果，附验证方法。存在依赖时关联前置任务或 Issue。
- 正文将当前需求、范围、AC 和需求变更表放在同一个“需求”章节。交付摘要保存阶段、候选版本、最近同步节点、阻塞和下一步，另附使用方法及证据索引。
- 开发中的新要求、决策和检查结果先累计到项目约定的本地待同步记录。没有约定时可使用 `.local/dev-records/issue-<编号>.md`，交付时提供路径。它只暂存尚未同步的内容；恢复工作时同时读取最新 Issue 和本地记录，保留他人的新结论，有冲突时明确列出。
- 每次实质需求变化记录日期、原结论、新结论、原因和受影响 AC。多次调整可以批量同步，但保留各次决定。保留原 AC 编号，新增条件使用新编号，取消的条件标记已取消并说明原因。
- 更新当前需求版本，重开受影响 AC，标记对应测试、review 或验收证据需重跑。未受影响的证据可以保留并说明适用范围。
- 相关 commit 和 PR 使用 `Refs #编号`。在交付检查点集中补充已推送且读回的提交链接，合并后补充最终提交。需要发布或后续验收时，不使用自动关闭关键词。

总体阶段使用待澄清、待开发、开发中、待验收、待发布、已发布待验收、已完成。单独记录测试、review、验收和部署结果，阶段不能代表这些检查已通过。结果可为通过、失败、未执行、阻塞、需重跑或不适用，不适用需说明原因。

## 初始化项目流程

仅在用户要求初始化流程时执行。复用现有模板和贡献指南；缺少模板时将本 skill 的模板复制到项目 `.github/ISSUE_TEMPLATE/change_request.md`。在现有指南中补入本地累计、检查点同步、提交关联和验收后关闭的约定，在 AGENTS.md 添加入口。将已有逐轮播报要求改为同一同步节奏，保留其他规则，不另建长期台账或自动化门禁。

模板合并到默认分支后，检查 GitHub 新建 Issue 页面中的模板选择、正文预填及预览。分支文件校验通过时，只能记录文件已验证，入口仍待验收。

## 推进与同步

整理需求时先更新本地待同步记录。首次建单、候选交付、需他人决策或影响协作的变化、正式验收及发布结果是远端同步节点。日常调整、自测和 review 修复不逐项发布进度评论。每个同步节点都合入已确认的待同步需求及变更，保持正文需求版本与各阶段结论一致。

候选交付以正式交接为触发条件。commit、push 并读回远端 SHA 后，将本轮需求变化、改动、测试、review、已有验收、剩余事项和 PR 链接一起同步。每次 push 不自动构成新节点；推送失败时保留未同步状态。未推送但确需交接时，明确未提交或未推送及现有证据范围。

用户要求“同步交付记录”时执行以上汇总，不顺带提交、推送、合并或部署。实际同步步骤、去重和失败恢复见 [Issue 同步规则](references/issue-sync.md)。

开发完成后进入测试和 review，再按条件验收、发布并最终验收。可使用 `dev-test`、`dev-review`、`dev-acceptance`、`dev-release`；未安装时按现有工具完成对应工作，不把其他 skills 当作安装依赖。

创建或更新远端 Issue 前，确认当前请求涵盖该操作。只要求起草时保留本地草稿。更新前重读远端，保留他人内容、需求历史和已交付候选的证据索引。同一节点内容无实质变化时跳过写入；每个正式交接至多一条摘要评论。写入后读回，结果不明时先查询再重试。使用现有连接器或已认证 CLI，以正文文件或结构化参数传递内容。不要写入凭据、客户数据或签名链接。

交付时先写当前结论，再写 Issue 或草稿位置、需求版本、未决项和下一步。使用短句和真实操作，区分计划、已实现、已验证与已部署。
