# 管理简单项目需求

以一个持续更新的 Issue 管理一个可独立交付的需求。先写清用户问题和可观察结果，再组织开发任务。

## 识别项目与需求

1. 读取仓库的 AGENTS.md、贡献指南、现有 Issue 模板和交付约定。确认实际仓库、默认分支及当前工作区，保留无关改动。
2. 按实际交付方式分类。一个 PR 合入默认分支、可以独立发布和回退时，采用简单流程。需要 UAT PR 再到 main PR、发布批次或跨系统协调晋级时，记录原因并移交项目专用 skills。不要自动生成两阶段流程。
3. 搜索已有 Issue。同一需求继续维护原 Issue，独立需求另建并关联。缺少访问能力时先写本地 Markdown 草稿，标记未同步，不阻塞无依赖的本地工作。
4. 写明谁在什么场景遇到什么问题、当前行为、预期行为和范围。缺陷补充复现步骤。影响正确性、数据或验收标准的未知项列为待澄清，其余使用可撤销的合理假设并说明。

需要了解这组 skills 的分工及设计理由时，读取 [设计说明](references/design.md)。日常建单不必加载它。

## 建立与维护记录

没有合适的现有结构时，使用 [Issue 模板](assets/change-request.md) 的章节。用模板创建 Issue 正文时去掉 YAML frontmatter 和填写提示。首次需求记为 r1，后续实质变更递增需求版本。

- 用稳定的 `AC1`、`AC2` 编号填写验收条件。每项写明前置条件、操作和可观察结果，不写“功能正常”。
- 将研发任务写成可独立验证的交付结果，附验证方法。存在依赖时关联前置任务或 Issue。
- 正文保存当前需求、范围、阶段、阻塞、下一步和使用方法。评论保存讨论，结论同步到正文。
- 需求变化时追加日期、原结论、新结论、原因和影响。保留历史及原 AC 编号，新增条件使用新编号，取消的条件标记已取消并说明原因。
- 更新当前需求版本，重开受影响 AC，标记对应测试、review 或验收证据需重跑。未受影响的证据可以保留并说明适用范围。
- 相关 commit 和 PR 使用 `Refs #编号`。只有推送并读回后才回填远端提交链接；合并后补充最终提交。需要发布或后续验收时，不使用自动关闭关键词。

总体阶段使用待澄清、待开发、开发中、待验收、待发布、已发布待验收、已完成。单独记录测试、review、验收和部署结果，阶段不能代表这些检查已通过。结果可为通过、失败、未执行、阻塞、需重跑或不适用，不适用需说明原因。

## 初始化项目流程

仅在用户要求初始化流程时执行。复用现有模板和贡献指南；缺少模板时将本 skill 的模板复制到项目 `.github/ISSUE_TEMPLATE/change_request.md`。在现有指南中补入建单、持续更新、提交关联和验收后关闭的约定，在 AGENTS.md 添加入口。保留已有规则，不另建重复台账或自动化门禁。

模板合并到默认分支后，检查 GitHub 新建 Issue 页面中的模板选择、正文预填及预览。分支文件校验通过时，只能记录文件已验证，入口仍待验收。

## 推进与同步

开发完成后进入测试和 review，再按条件验收、发布并最终验收。可使用 `dev-test`、`dev-review`、`dev-acceptance`、`dev-release`；未安装时按现有工具完成对应工作，不把其他 skills 当作安装依赖。

创建或更新远端 Issue 前，确认当前请求涵盖该操作。只要求起草时保留本地草稿。使用现有连接器或已认证 CLI；更新前重新读取正文，保留他人更新与历史，写入后读回。使用正文文件或结构化参数，避免把正文拼入 shell。不要写入凭据、客户数据或签名链接。

交付时先写当前结论，再写 Issue 或草稿位置、需求版本、未决项和下一步。使用短句和真实操作，区分计划、已实现、已验证与已部署。
