# Issue 同步规则

在创建需求、集中同步交付记录或初始化项目 tracker 规则时使用本规则。

## 记录位置

Issue 正文保存已同步的需求、需求变更表和当前交付摘要。正文注明最近同步节点、时间和候选版本。评论保留讨论和正式交接摘要，讨论结论归入正文。

开发中的新增要求、决策、测试和 review 结果先写入项目约定的本地待同步记录。没有约定时可使用 `.local/dev-records/issue-<编号>.md`，并明确交付该路径。恢复工作时读取最新 Issue 与该记录，核对未同步内容，避免覆盖他人新决定。

本地记录包含需求版本、各次实质变更、稳定 AC 编号、候选 SHA 或未提交改动指纹、环境、各阶段结论及证据位置。成功同步后记录远端位置及同步范围，后续只累计新增内容。它不成为另一套独立需求台账。

## 同步节点

| 节点 | 同步内容 |
| --- | --- |
| 首次建立需求 | 目标、范围、初始需求版本、AC 和待澄清项 |
| 正式交付候选供 review 或验收 | commit、push 并读回的 SHA，本轮需求变更、实现摘要、检查结论、剩余事项及 PR |
| 需他人决策或影响协作的范围、关键决定、阻塞变化 | 问题、影响、当前已知状态和解除条件，可在 push 前同步 |
| 交接尚未提交或推送的工作 | 实际代码状态、本地记录和证据位置，明确未同步的改动 |
| 一轮正式验收形成结论 | 阶段、实际版本与环境、AC 结果、失败或阻塞及下一步 |
| 合并、部署、回退结束或中止 | 最终提交、实际运行版本、冒烟、异常与恢复结果及剩余验收 |

普通 push、每次对话、UI 微调、单条测试和 review 修复不单独触发同步。连续完成的合并、部署及验收可在同一次交接集中汇报；需要介入的失败及时同步。

正式候选交付前核对证据是否覆盖最终提交，代码变化后刷新受影响项。push 失败不回填远端提交链接，不标记候选已交付。正式验收和部署结果有变化时，即使 SHA 未变也应同步。

## 集中同步

1. 确认当前请求允许远端更新。只要求起草时保留草稿；同步记录不授权 commit、push、合并、部署或关闭 Issue。
2. 重新读取正文及本次交接已有摘要。每个节点都将已确认的待同步需求及变更合入“需求”章节，再更新相应阶段结论，保持需求版本一致。保留他人内容、各次需求决定和既有候选证据索引。冲突无法确定时保留待澄清内容，不覆盖原结论。
3. 比较需求版本、候选 base/head 或产物、环境、各阶段结果、阻塞和下一步。同一节点没有实质变化时跳过写入，时间戳变化不构成同步理由。不能仅按 SHA 判重。
4. 更新正文。每个正式交接至多一条摘要评论，已有本次摘要时复用它。普通汇总只更新正文；保留原有历史评论。完整日志和截图放在证据位置，正文保留结论及索引。向协作者交接时提供可访问的证据，只有本地文件时说明限制。
5. 读回正文和需要的摘要评论，再将对应本地内容标为已同步。部分成功时只确认已读回的部分，保留其余待同步。响应不明时先查询现有正文和摘要，确认后再补写，避免重复评论。

同步失败时继续可以独立完成的本地工作，说明哪些内容尚未同步，在下一有用检查点重试。不要删除旧评论或将计划、mock、未执行项目改写为实际通过。

## 项目入口

仅在用户要求初始化或更新项目流程时修改项目规则。在现有 tracker 文档中写明上述节点，在 AGENTS.md 保留入口。处理原有“每轮完成都回填”等冲突规则，统一改为本地累计、检查点同步。

其他 dev skills 各自保留必要的同步边界，无需强制安装本 skill。项目没有集中同步工具时，直接按这些步骤完成对应节点。
