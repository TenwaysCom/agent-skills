# 测试简单项目改动

用当前需求和实际改动选择检查，记录真实运行结果。测试通过表示已检查的技术行为通过，业务验收和部署另有结论。

## 确认测试对象

1. 读取项目测试约定、Issue 当前需求及 AC、实际 base/head diff。记录需求版本、候选完整 SHA 和未提交改动。有未提交改动时保留 diff 或产物指纹，不能把结果记到干净 HEAD 上。
2. 确认测试环境、依赖和相关配置。已有 UAT 晋级或两次 PR 的项目使用其专用测试流程，只整理当前证据和交接信息。
3. 按 AC 与变更影响选择正常、边界、异常和回归检查。优先执行项目已有检查；补测试时验证用户可观察行为，避免只断言实现细节。可撤销的低影响文档调整通常不需要新增应用测试。

## 执行与记录

逐项执行需要的检查，保留命令或操作、退出状态、实际结果和日志位置。区分执行通过、失败、未执行、被阻塞。外部集成只有 mock 结果时明确标记，不能填写真实集成已通过。

每条记录关联 AC 或风险，包含需求版本、代码版本、环境与关键配置、检查动作、实际结果和证据。配置可用不代表外部调用成功，页面返回成功不代表业务写入成功；需要时读回实际对象。

出现失败时，定位是当前改动、环境还是已有问题。保留失败证据和受影响范围。不要跳过断言、放宽预期或只重试到绿色；仅对有依据的临时故障进行有限重试，记录首次失败及重试结果。修复代码后复跑受影响检查。

完成项目规定的必需检查后，只有新的改动、失败或未消除的疑点才扩大或重复测试。使用隔离数据，按项目约定清理临时资源；异常中断留下资源时记录清理方法。

## 提测结论

将结果更新到已有 Issue 的“验证与交付”，缺少远端权限时保留本地报告并标记未同步。更新前读最新正文，保留他人内容，写入后读回。当前请求未涵盖远端写入时仅交付草稿。

代码、依赖、配置或需求变化后，检查旧证据的适用范围。受影响项标记需重跑并重新执行。对最终候选提交记录有效结果，不用旧 SHA 的绿色结果替代。

交付候选版本、已覆盖 AC、检查结果、未覆盖场景、阻塞和下一步。必需检查失败或未执行时不能结论为提测通过；项目允许带限制提测时写清限制及决定者。测试通过后仍保留独立的 review、业务验收、合并及部署状态。

需要业务确认时可使用 `dev-acceptance`，需要审查改动时可使用 `dev-review`。其他 skills 未安装时直接交付报告，不阻塞本 skill。
