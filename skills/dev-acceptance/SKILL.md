# 验收简单项目交付

逐项验证用户实际得到的行为。区分预览验收和最终交付验收。

## 选择验收阶段

读取最新 Issue、本地待同步的需求及 AC、使用方法、测试及 review 结果。以最后已确认的需求为准，冲突列为待澄清。确认需求版本、待验收代码或产物版本、环境、入口及执行者。项目使用独立 UAT 晋级、两次 PR 或发布批次时，按专用验收流程交接，不自行晋级。

- 预览验收检查候选环境中的 AC，通过后可以进入待发布。生产部署相关条件继续保持未完成。
- 最终交付验收检查实际交付环境及运行版本。合并后的模板、安装包或实际入口，需要在其生效位置验证。
- 项目要求业务负责人、QA 或客户确认时，记录真实执行者、结论、时间和证据。agent 的操作记录不能代替该人的批准。没有指定人工确认要求时，agent 可以执行可观察的验收并明确身份。

## 逐项执行

按 AC 的前置条件和操作，通过真实界面、命令或集成入口检查可观察结果。复用技术测试证据时说明它覆盖哪一条件；业务流程与实际环境仍需对应证据。记录需求版本、代码或产物版本、环境、执行者、实际结果和证据位置。

需要有副作用的业务操作时，使用已授权的测试数据及环境。权限、数据或外部服务不足时，标记阻塞或未执行并说明解除条件，不能勾选通过。

AC 使用通过、失败、未执行、阻塞或需重跑。条件取消或不适用时，必须记录范围决策、原因和决定者；不能以不适用消除失败。需求或版本变化后重开受影响项，保留旧证据为历史。

失败时写出复现步骤、实际与预期差异、影响及回到开发或发布处理的下一步。同一需求修复继续使用原 Issue；独立缺陷另建并关联，保留原需求未交付的事实。

## 同步验收结论

逐项结果先累计到本轮本地待同步记录。沿用项目约定的记录位置，没有约定时可使用 `.local/dev-records/issue-<编号>.md`，交付时提供路径。一轮正式验收形成通过、失败或阻塞结论时，集中同步实际版本、环境、执行者、AC 结果和下一步，不逐条发布 AC 进度。需他人决策、影响协作的阻塞或中途交接及时同步。即使 SHA 未变，新的验收结论仍需更新；预览或实际环境验收不以新 commit、push 为前提。

远端更新须在当前授权范围内。每个节点都合入已确认的待同步需求及变更，保持正文需求版本与验收结论一致。写入前重读正文，保留他人内容、需求历史、旧候选证据及其他阶段状态。同一节点无实质变化时跳过写入，正式交接至多一条摘要。写入后读回，再将对应本地内容标为已同步；部分成功时保留其余待同步，结果不明时先查询。缺少权限或访问能力时保留本地报告并标记未同步。

## 完成交付

全部适用 AC 通过后，检查以下条件再判定已完成。

- 验收证据仍覆盖当前需求及实际交付版本。
- 项目要求的测试、review 和人工确认已满足。
- 需要部署时，已有实际部署版本读回及关键业务路径结果。文档或纯本地工具无应用部署时说明原因，并验收其交付入口。
- 使用方法、配置及必要回退方法与实际实现一致。
- commit、PR、最终合并或发布版本已关联，远端链接可读回。

满足条件但没有关闭授权时，交付可关闭结论及本地更新文本。已授权关闭时，先更新 Issue 正文并读回，再关闭并确认状态。不能因 PR 合并、CI 绿色或一次预览验收而提前关闭。

只完成预览验收时写待发布，已部署但未完成实际环境验收时写已发布待验收。交付结果先写阶段和结论，再写逐项结果、证据、阻塞和下一步。需要发布时可使用 `dev-release`，无需强制安装。
